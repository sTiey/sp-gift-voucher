# 01 · ระบบคิดยังไง

เอกสารนี้อธิบาย **ภาพใหญ่** ว่าทำไมระบบถูกวางแบบนี้ ก่อนจะลงรายละเอียด
ถ้าจะแก้อะไรที่กระทบหลายจุด อ่านหน้านี้ก่อน

---

## 1. คูปอง 1 ใบคืออะไร

คูปอง = **ข้อมูล 1 ก้อน** ที่ตอบ 4 คำถาม

| คำถาม | เก็บไว้ที่ | ตัวอย่าง |
|---|---|---|
| ได้อะไร | `kind` + `value` | ลด 15% · ลด 500 บาท · ส่งฟรี |
| ใครใช้ได้ | `audience` | เฉพาะพาร์ทเนอร์ · เฉพาะคุณสมชาย |
| ใช้ได้เมื่อไหร่/อย่างไร | `validFrom` `validUntil` `conditions` `limits` | ซื้อครบหมื่น · ถึงสิ้นปี · คนละใบ |
| หน้าตายังไง | `design` | ธีมเหล็ก · มีป้าย PARTNER |

3 ข้อแรกคือ **ตรรกะ** ข้อสุดท้ายคือ **หน้าตา** — แยกกันเด็ดขาด
เปลี่ยนหน้าตาไม่ทำให้คิดเงินผิด และเปลี่ยนเงื่อนไขไม่ทำให้หน้าเว็บพัง

---

## 2. วงจรชีวิต

```
   [แอดมิน]                [ลูกค้า]                    [หน้าร้าน / ตอนจ่ายเงิน]

   ออกคูปอง  ──ส่งลิงก์/QR──▶  เปิดดูบนมือถือ  ──แสดงรหัส──▶  ตรวจ  ──▶  ตัดสิทธิ์
      │                            │                                        │
      │                            └──── กดใช้เองในแอป ─────────────────────┘
      │
      └── ยกเลิกได้ทุกเมื่อ (void)
```

### สถานะที่ "เก็บ" กับสถานะที่ "เห็น" ไม่ใช่อันเดียวกัน

นี่คือการตัดสินใจที่สำคัญที่สุดในระบบ

**สถานะที่เก็บ** (`state`) = สิ่งที่ *คน* ทำ มี 5 ค่า
`draft` · `issued` · `reserved` · `redeemed` · `void`

**สถานะที่เห็น** (`status`) = คำนวณสด ๆ ทุกครั้งจาก state + วันที่ + โควตา มี 7 ค่า
`draft` · `scheduled` · `active` · `reserved` · `redeemed` · `expired` · `void`

ทำไมต้องแยก — ถ้าเก็บ `expired` ลงฐานข้อมูล จะต้องมีงานเบื้องหลังคอยไล่อัปเดต
คูปองทุกใบทุกวัน งานแบบนั้นพังง่ายและช้า **คูปองเป็นล้านใบก็ไม่ต้องแตะเลย**
ถ้าคำนวณจากวันหมดอายุตอนที่มีคนถามเท่านั้น

โค้ดอยู่ที่ `src/core/lifecycle.js` ฟังก์ชัน `deriveStatus()`

## 3. ทำไมแยกเป็น 3 ชั้น

```
┌─────────────────────────────────────────────────┐
│  หน้าตา     tokens/ · styles/ · ui/             │  ← เปลี่ยนบ่อยสุด
├─────────────────────────────────────────────────┤
│  ตรรกะ      core/rules.js · lifecycle.js        │  ← เปลี่ยนตามโปรโมชัน
├─────────────────────────────────────────────────┤
│  ข้อมูล     core/schema.js                      │  ← เปลี่ยนน้อยสุด
└─────────────────────────────────────────────────┘
       ชั้นบนรู้จักชั้นล่าง · ชั้นล่างไม่รู้จักชั้นบน
```

ผลที่ได้จริง ๆ:

- **เปลี่ยนธีมทั้งระบบ** = แก้ไฟล์ค่าสีไฟล์เดียว ไม่แตะโค้ดสักบรรทัด
- **เอาตรรกะไปรันบนเซิร์ฟเวอร์** = ก๊อป `core/` ไปทั้งโฟลเดอร์ มันไม่รู้จัก `document`
  หรือ `window` เลยสักตัว → หน้าเว็บกับหลังบ้าน**คิดเลขตรงกันแน่นอน** เพราะใช้โค้ดชุดเดียวกัน
- **เพิ่มชนิดคูปองใหม่** = เติมที่ `schema.js` แล้วไล่ตามที่ระบบฟ้อง

## 4. ที่เก็บข้อมูลเปลี่ยนได้โดยไม่แตะหน้าเว็บ

`store.js` แยกเป็น 2 ชั้น

```
หน้าเว็บ  →  VoucherService  →  Adapter  →  ที่เก็บจริง
             (คำสั่งที่ใช้งาน)   (5 เมธอด)
```

Adapter มีสัญญาแค่ 5 อย่าง: `list` `get` `put` `remove` `clear`

| Adapter | เก็บที่ไหน | ใช้ตอน |
|---|---|---|
| `MemoryStore` | ในหน่วยความจำ | เขียนเทสต์ |
| `LocalStore` | ในเบราว์เซอร์ | ต้นแบบ / เดโม |
| `HttpStore` | API ของบริษัท | ของจริง |

เปลี่ยนจากเดโมเป็นของจริง = แก้บรรทัดเดียว

```js
new VoucherService(new LocalStore())        // ตอนนี้
new VoucherService(new HttpStore('/api'))   // ของจริง
```

## 5. ข้อความบนจอทุกคำเป็น "ค่าที่แก้ได้"

ไฟล์ `src/core/strings.th.js` เก็บข้อความบนจอ**ทุกคำ** ไฟล์ UI ห้ามพิมพ์ข้อความลงไปตรง ๆ

```js
t('status.active')        // "ใช้ได้"
t('reject.min_spend')     // "ยอดซื้อยังไม่ถึงขั้นต่ำ"
```

ได้อะไร:
1. อยากเปลี่ยนคำว่า "ใช้สิทธิ์" เป็น "แลกเลย" ทั้งระบบ → แก้ที่เดียว
2. ทำภาษาอังกฤษเพิ่ม → ก๊อปไฟล์เดียวแล้ว `setLocale('en')`
3. ลืมใส่คำไหน จะเห็นเป็นคีย์ดิบบนจอทันที (เช่น `status.foo`) ไม่ใช่ช่องว่างเงียบ ๆ

## 6. ตรรกะทั้งหมดรวมอยู่ที่ฟังก์ชันเดียว

```js
evaluate(voucher, context)
```

ใส่ "คูปอง 1 ใบ" กับ "สถานการณ์ตอนนี้" (ยอดเงิน · ลูกค้าคือใคร · ช่องทางไหน)
แล้วได้คำตอบทุกอย่าง:

```js
{
  ok: false,
  reasons: ['min_spend'],   // เรียงตามความสำคัญ reasons[0] คือข้อที่ควรโชว์
  discount: 0,
  payable: 24000,
  freeShipping: false,
  freeItems: 0,
}
```

เป็น **ฟังก์ชันบริสุทธิ์** — ใส่อะไรเข้าไปก็ได้คำตอบเดิมเสมอ ไม่แตะฐานข้อมูล
ไม่แตะหน้าจอ ทำให้เขียนเทสต์ได้ตรง ๆ และเอาไปรันฝั่งเซิร์ฟเวอร์ได้ทันที

> ⚠️ ผลจากหน้าเว็บใช้ **แสดงผล** เท่านั้น การตัดสินจริงต้องเกิดฝั่งหลังบ้าน
> เหตุผลอยู่ใน [05 ความปลอดภัยและกับดัก](05-ความปลอดภัยและกับดัก.md)

## 7. เส้นทางที่ผู้ใช้เดินจริง

### ลูกค้า
1. ได้ลิงก์ทาง LINE / อีเมล / ในแอป → เปิด `voucher.html?c=รหัส`
2. เห็นใบคูปอง + QR + เงื่อนไข
3. **กดค้าง 1 วินาที** เพื่อใช้สิทธิ์ (กดค้างเพราะย้อนกลับไม่ได้ — กดโดนพลาดครั้งเดียวคูปองหาย)
4. ใบฉีกออกเป็นสองท่อน แล้วขึ้น **รหัสยืนยันสด 4 หลัก** ให้พนักงานดู

### พนักงานหน้าร้าน
1. เปิด `staff.html`
2. พิมพ์รหัสที่ลูกค้าแสดง (ระบบใส่ขีดให้เอง · พิมพ์ผิดระบบรู้ทันที)
3. ใส่ยอดก่อนลด → เห็นเลยว่าลดเท่าไหร่ ต้องเก็บเท่าไหร่
4. ถ้าไม่มั่นใจ ให้ลูกค้าอ่านรหัสยืนยันสด 4 หลัก แล้วกรอกเทียบ
5. กด "ตัดสิทธิ์"

### แอดมิน
1. เปิด `admin.html` กรอกฟอร์ม → เห็นใบตัวอย่างเปลี่ยนตามทันที
2. ใส่จำนวนใบ → กดสร้าง → ได้รหัสไม่ซ้ำกันทั้งชุด
3. ดาวน์โหลดเป็น JSON เอาไปเข้าระบบส่ง LINE/อีเมลต่อ
